# Feature Specification: 完成复盘提速且保持业务逻辑不变

**Feature Branch**: 未创建；本功能通过目录标识，与分支名称无关

**Created**: 2026-09-17

**Status**: Ready for planning

**Input**: User description: "我发现我每天点击完成复盘时速度真的很慢很慢。你帮我出一个改造计划加快执行速度，但要求业务逻辑不能变。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 更快完成每日复盘 (Priority: P1)

作为每日记录复盘的用户，我希望点击“完成复盘”后更快看到已完成状态和更新后的列表，同时本次编辑内容、归档结果和账户结果与优化前完全一致。

**Why this priority**: 这是用户每天重复遇到的等待，也是本次优化的主要目标。

**Independent Test**: 从相同的未完成记录及编辑内容开始，分别使用优化前后版本完成复盘，测量点击至完成界面更新的耗时，并对比全部业务结果。

**Acceptance Scenarios**:

1. **Given** 最新复盘日尚未完成且填写内容符合现有校验规则，**When** 点击完成复盘，**Then** 保存当前内容，完成新闻归档和账户处理后才呈现已完成状态，等待时间满足 SC-001。
2. **Given** 点击完成前修改了操作计划、大盘、板块、新闻总结或深度总结，**When** 完成复盘，**Then** 所有应保存的最新编辑内容与原流程一致，无遗漏、覆盖或旧值回写。
3. **Given** 当日新闻和操作计划数量较多，**When** 完成复盘，**Then** 全量内容均按原规则处理，不通过少处理数据或提前报成功缩短等待。
4. **Given** 内容不满足原有校验规则，**When** 尝试完成，**Then** 原有阻止条件和错误含义保持一致，不为提速放宽校验。

---

### User Story 2 - 保存和完成异常仍可按原方式恢复 (Priority: P1)

作为复盘用户，我希望提速后仍能辨别完成是否成功；出现失败时保留原有的数据状态、错误提示含义和重试路径。

**Why this priority**: 性能提升不能以丢失编辑内容、误报完成或改变失败后的数据为代价。

**Independent Test**: 在相同业务阶段注入相同故障，对比优化前后的已保存内容、复盘状态和再次操作结果。

**Acceptance Scenarios**:

1. **Given** 草稿保存阶段失败，**When** 用户点击完成，**Then** 不继续完成复盘，保留原有错误处理方式。
2. **Given** 草稿已保存但新闻归档或账户处理失败，**When** 完成流程返回失败，**Then** 不提前标记复盘完成；已生效的写入范围与原流程在对应故障点一致。
3. **Given** 上次完成失败且故障已解除，**When** 用户再次操作，**Then** 按原规则完成，不新增新闻或操作计划重复记录，不改变账户计算规则。
4. **Given** 后台已成功完成但完成反馈或列表刷新异常，**When** 用户刷新或再次操作，**Then** 真实业务状态和原有重复操作语义保持一致。

---

### User Story 3 - 其他复盘入口保持兼容 (Priority: P2)

作为使用历史记录和批量复盘的用户，我希望每日完成提速不影响单独保存草稿、历史复盘和自动回填。

**Why this priority**: 多个入口共享复盘处理能力，需要防止性能改造产生其他业务回归。

**Independent Test**: 分别执行单独保存、手动历史复盘和多日期批量复盘，与原版本对照验证。

**Acceptance Scenarios**:

1. **Given** 用户只想保存草稿，**When** 点击保存，**Then** 保存及后续可见内容保持原样，不自动完成复盘。
2. **Given** 用户手动完成历史日期，**When** 保存并完成，**Then** 历史日期的内容、归档和账户处理符合原规则，不改变最新日与历史日操作计划同步的区别。
3. **Given** 存在多个历史待复盘日及最新记录，**When** 批量自动复盘，**Then** 仍保留全部记录中的最新日期，按从早到晚处理其他符合条件的日期，保持自动回填、保留已有内容和单日失败继续的规则。
4. **Given** 最新记录已经完成或仅剩最新记录待复盘，**When** 执行批量复盘，**Then** 前者不额外保留另一历史待复盘日，后者不自动完成最新记录。

### Edge Cases

- 当日没有可归档新闻，或新闻分析未指定来源新闻：分别保留原有空结果和新闻时间窗口筛选规则。
- 来源新闻缺失、重复新闻标识或新闻类型需要归一化：保持原有筛选、排序、覆盖及空值处理结果。
- 操作计划为空、包含同一标的的不同账户、存在无效标的或缺失账户：保持原有默认账户、校验和去重规则。
- 无行情、无仓位、当日新增标的或停用账户：保持原有账户影响计算、排除条件和“暂无数据”结果。
- 草稿中显式清空的结构化字段与从未填写的字段：仍按原规则区分，不改变回填优先级。
- 快照已有、复盘已完成后再次手动完成、连续点击或多个页面操作：不得引入额外重复数据或新的覆盖规则，以原版本对应场景为对照。
- 每个写入阶段中途失败、结果反馈丢失和重试：比较对应阶段的数据变化和恢复结果，不能只验证最终成功路径。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须缩短每日手动“完成复盘”的端到端等待时间；计时包含保存、完成处理和用户最终可见的界面更新。
- **FR-002**: 系统必须保持现有内容校验、保存字段、默认值、排序、去重、空值和显式清空语义；不得遗漏本次编辑。
- **FR-003**: 系统必须保持归档新闻的选取范围、来源优先级、时间窗口、筛选条件、内容归一化及重复记录处理规则。
- **FR-004**: 系统必须保持每日及实时操作计划的内容和同步条件，尤其保留最新复盘日与历史日期的区别。
- **FR-005**: 系统必须保持账户影响计算、仓位解释、新增标的排除、缺失数据处理、快照来源、资产及现金同步规则。
- **FR-006**: 系统必须在原有必要业务处理全部成功后才能将复盘标记完成；不能用提前成功反馈或未完成的后台处理替代真正完成。
- **FR-007**: 系统必须保持相同故障阶段的错误含义与重试结果；未经用户明确同意，不改变部分成功或回滚范围。用户已于 2026-09-20 明确同意放宽回滚范围，据此修订后的失败语义为：写入按批提交，**批次内失败整体回滚**，跨批次之间仍可能留下部分完成状态。以下三条保持不变——错误的类别与含义不变；不得提前宣告成功；清除故障后重试，最终业务状态必须与原逐条流程收敛一致。整表重建表的自增主键绝对值不属于业务内容（原流程每次完成复盘也会推进），只要求行数、相对顺序与唯一性一致。
- **FR-008**: 单独保存草稿、历史手动复盘、已完成记录的现有编辑能力及历史批量复盘必须保持兼容，批量日期顺序和最新日保护不变。
- **FR-009**: 完成后用户看到的列表和复盘状态必须与保存结果一致；不新增需要用户操作的步骤。
- **FR-010**: 优化前后必须基于相同输入和初始业务数据进行对照；比较内容、关联关系、记录数量、状态和账户数值。自动生成的标识与时间不要求字面相同，但生成规则、关联关系、先后关系及更新条件必须一致。
- **FR-011**: 必须提供普通及较大数据量场景的前后耗时分布、成功率和结果一致性证据；未达到目标时如实说明，不以动画或提前关闭界面代替实际耗时改善。
- **FR-012**: 本次范围是性能改造规格及后续方案设计；不新增复盘业务功能，不更换分析模型、不重新定义财务计算，不改变权限和历史数据。

### Key Entities *(include if feature involves data)*

- **复盘记录**: 某日期的新闻总结、大盘盘点、板块轮动、操作计划、深度总结及完成状态。
- **归档新闻**: 与复盘日期对应的新闻集合及保存时的内容和处理状态。
- **操作计划**: 按账户、标的组织的每日计划及按原规则同步的实时计划。
- **账户快照与影响结果**: 完成时保存的账户资产、现金、影响估算、来源及关联账户。
- **性能对照记录**: 在固定输入、初始状态和访问条件下记录的等待时间、成功失败结果及业务一致性比较结论。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在普通工作量组（50 条新闻、20 条操作计划、3 个账户）及较大工作量组（200 条新闻、40 条操作计划、3 个账户）中，各完成至少 30 次独立对照；优化后点击至成功界面更新的中位耗时分别降低至少 30%，P95 耗时分别降低至少 20%。
- **SC-002**: 对全部用户场景、边界情况和成功路径进行对照，业务结果一致率为 100%；新闻、计划和快照无遗漏、无新增重复、无数值偏差。
- **SC-003**: 对草稿保存、新闻归档、账户快照、账户同步及完成状态写入阶段分别注入故障，各场景的已生效数据、完成状态和重试结果与原流程一致率为 100%，提前宣告成功次数为 0。
- **SC-004**: 在无故障的性能对照样本中完成成功率为 100%；全部兼容场景通过；用户完成一次复盘所需操作步数不增加。

## Assumptions

- 业务基线为本次规格编写时工作区的现有行为，包含已经发布的历史自动回填与最新日期保护；实现前保存可重复验证的基线，不能将其他未确认业务修复混入提速。
- 用户尚未同意改变失败回滚行为，因此“业务逻辑不能变”默认包含失败及部分写入状态。若后续方案依赖不同失败语义，必须先更新需求并取得用户明确同意。
- 性能目标和两组工作量是本规格采用的默认验收标准，并非已测结果；若实测证明与真实使用量不符，在实现前依据记录调整规格，不能在验收时静默降低目标。
- 对照使用相同设备、浏览器、网络条件、服务环境及起始数据；每轮恢复未完成状态，交错测试两个版本，分别记录首次和后续运行，避免把已完成记录的跳过结果当作提速。
- 计时起点为有效点击，终点为必要业务处理成功且界面完成更新；剔除故障样本必须说明原因，故障样本另外计入可靠性验证。
- 真实账户和新闻属于现有用户数据，性能测试使用隔离副本或合成数据，不以反复完成真实历史复盘作为压测方式。
- 本轮只产出规格和质量检查；技术方案、任务拆分、代码修改及部署属于后续阶段。
- 项目宪章目前仍为未填写模板，没有可执行的已批准项目原则；以上用户约束作为本功能基准，不把模板示例视为实际规则。

### Planning refinement — 2026-09-18

- 大工作量成功对照组由 100 条计划修正为 40 条计划，新闻仍为 200 条；原实现无法在 100 条计划下完成，因此该输入不能用于成功耗时对比。100 条计划移至故障兼容性用例，保持原有失败阶段与已保存数据范围。
- 本次不修复该既有容量限制。中位数降低 30%、P95 降低 20% 的目标不变。技术证据见 research.md。
